# PART 1 — CURRENT-SYSTEM AUDIT

## 1.1 Dispatch as it actually works

The whole booking path is Socket.IO, not REST. `apps/keke_backend/src/sockets/socket_handler.ts` is
a 2,183-line class that owns dispatch, ride lifecycle, coordination and SOS.

**Request → assignment**

| Step | Where | Notes |
|---|---|---|
| `ride:request` received | `socket_handler.ts:439` | **`rideId` is generated by the passenger app**, not the server |
| Passenger active-ride guard | `socket_handler.ts:450–498` | Redis `SET NX` on `passenger:active:<id>` (3h TTL) + a DB backstop over `['searching','accepted','arrived','in_progress','started']` |
| Ride row created | `socket_handler.ts:503–515` | status `searching`, plus a 4-char `pickupCode` |
| `startDispatchLoop` | `socket_handler.ts:1931` | creates a `DispatchRun`, arms a hard lifetime timer, runs the orchestrator |
| Rounds / tiers | `services/dispatch_orchestrator.ts:198` | at most **2 rounds** (`MAX_SUPPORTED_ROUNDS`), tiers `[2, 3.5, 5]` km then `[5, 6.5]` km |
| Eligibility | `services/driver_eligibility_service.ts:47` | approved (not suspended/rejected) · cash debt `< ₦2,000` · not already on `accepted/arrived/in_progress` |
| Atomic reservation | `services/dispatch_service.ts:209` | `SET driver:reserved:<id> <rideId> EX 30 NX` — issued **before** any offer leaves |
| Offer delivery | `socket_handler.ts` ports + `notification_service.ts` | socket emit + FCM multicast; delivery evidence is recorded honestly, never inferred |
| Assignment | `socket_handler.ts:734–745` | conditional `UPDATE ... SET driverId, status='accepted' WHERE rideId=? AND status='searching' RETURNING *` — the single arbiter |
| Failure | `socket_handler.ts:1978` | `finalizeUnsuccessfulDispatch` sets status `failed`, emits `ride:failed`, releases the passenger slot |

**Timing budget (defaults, `config/dispatch_config.ts`):** offer window 15 s, empty-tier pause 3 s,
round gap 1 s, re-offer cooldown 45 s, **total search lifetime 110 s**, candidate limit 10.

**Redis keys in play**

```
drivers:locations              GEO set of driver positions (heartbeat ~12s)
driver:available:<driverId>    'true', EX 45   → the availability gate
driver:lastseen:<driverId>     EX 24h          → admin "last seen"
driver:offline:<driverId>      deliberate-offline tombstone
driver:reserved:<driverId>     <rideId>, EX 30, NX
ride:<rideId>:lock             <driverId>
passenger:active:<passengerId> <rideId>, EX 3h, NX
ride:search_context:<rideId>   round + radius mirror for the passenger map feed
```

**Evidence.** `DispatchEvidence` (in-memory, per run) is projected into the `DispatchEvent` table
(`models/DispatchEvent.ts`) through `dispatch_event_projection.ts`. The enum is deliberately honest —
there is no "driver saw it" event; `DEVICE_OFFER_ACK` is the only true device-level proof, and
`OfferDeliveryState` grades confidence rather than upgrading it. **This is the template Park Dispatch
evidence must follow.**

**Stale-ride recovery.** `stale_ride_service.ts`, `stale_ride_sweeper.ts`, `ride_cleanup_service.ts`,
`ride_activity_service.ts` and `ride_coordination_contract.ts` implement a two-sided decision model: a
delayed ride is never cancelled on a timer alone; both parties are prompted, and `staleDecisionPromptedAt`
is the invariant that makes silent cancellation impossible. Documented in `docs/ride_coordination_contract.md`.

### 1.1.1 Two structural facts that constrain the design

**(a) Dispatch state is in-process and single-node.** `dispatchRuns`, `activeDispatches`,
`dispatchPayloads`, `dispatchTimers`, `driverRideMap` and `earlyEndTimers` are all
`Map`s on the `SocketHandler` instance (`socket_handler.ts:182–199`). A dispatcher action that arrives
over HTTP on a *different* process could not see or abort the run. Today there is exactly one backend
process, so this works — but Park Dispatch adds a second actor class, and any future horizontal scale
breaks it. Park claim/assignment state therefore belongs in **Redis + Postgres, never in a Map**.

**(b) There is no park, zone, dispatcher, badge or device-binding concept anywhere.** Repo-wide search
found only an unrelated `'Awka Motor Park'` string literal in a passenger demo list
(`booking_sheet.dart:999`). Everything in this proposal is new surface.

## 1.2 Driver model

`User` (`models/User.ts`): uuid id, unique email, **nullable phone**, password, first/last name,
`role ∈ {passenger, driver, admin}`, `emailVerified`.

`DriverProfile` (`models/DriverProfile.ts`): `userId` PK, first/last name, `vehiclePlate`,
`vehicleModel`, `status ∈ {pending_documents, pending_review, approved, rejected, suspended}`,
document URLs (`licenseUrl`, `idCardUrl`, `vehiclePaperUrl`, `photoUrl`), `nin` + `ninVerified`,
`ratingSum`/`ratingCount`.

Gaps relevant to parks:
- **No unit number**, no home park, no operating area.
- **Phone is optional** — yet the passenger's "call driver" action depends on it
  (`socket_handler.ts:774`). For a no-smartphone driver a working phone number is not optional.
- Online-ness is purely a Redis heartbeat side-effect. There is no persisted "this driver works
  through a park" flag, and no representation of a driver who cannot emit GPS at all.
- Device relationship is only `DeviceToken` (FCM tokens per user). No device binding, no attestation.

## 1.3 Wallet, payments and commission

`Wallet` (`models/Wallet.ts`): one row per `userId` with `passengerBalance`,
`driverAvailableBalance`, `driverPendingBalance`, `driverCommissionDebt`.
`LedgerEntry` is append-only with `balanceBefore`/`balanceAfter` on every row — a genuine ledger.

Commission (`wallet_service.ts:238`): fare is treated as **inclusive** of the platform fee —
`driverNet = fare / (1 + pct/100)`, `commission = fare − driverNet`, `platformFeePercent` default 10
(overridable via the `Setting` table).

- **Cash ride** (`_postCashRideFinancials`): `CASH_RECEIVED` audit row (balance unchanged) →
  `COMMISSION_CHARGE` against `driverAvailableBalance` → any shortfall becomes `driverCommissionDebt`
  → `PLATFORM_REVENUE` entry.
- **Wallet ride**: debit passenger → credit driver net → recover debt from those earnings →
  `PLATFORM_REVENUE` entry.
- Platform revenue is **entry-only** (`walletId: 'PLATFORM'`, before/after both `0`). There is no
  platform balance to reconcile against, which matters for park cash settlement.

Debt thresholds (`wallet_service.ts:18–20`): warn ₦1,000 · cash-block ₦2,000 · hard-block ₦5,000.
**`DEBT_HARD_BLOCK` is imported but never enforced anywhere** (`socket_handler.ts:30` is its only
reference) — it is dead today.

Money in/out: Paystack top-up (`finance_routes.ts`, `paystack_service.ts`, HMAC-verified webhook),
`PayoutRecord` with a manual admin-driven `pending → processing → success/failed` flow, and
`repayDebtFromBalance` for driver self-service repayment. **There is no cashier role, no cash-in
recording, and no bank-transfer reconciliation.**

## 1.4 Passenger flow

`BookingStep` (`booking_state.dart:7`): `loading, idle, selectingPickup, selectingDestination,
selectingDestinationOnMap, previewEstimate, searching, confirmed, arrived, started, completed`.

On assignment the passenger receives `ride:assigned` with `driverDetails = {name, plate, model, phone,
photoUrl, rating, ratingCount}` plus `pickupCode` (`socket_handler.ts:770–784`). Live tracking is
`driver:location_update`, emitted as a side-effect of the **driver's** heartbeat
(`socket_handler.ts:423`). Review/rating exists (`RideReview`, `POST /rides/:rideId/review`).

**Consequence: with no driver app there is no heartbeat, therefore no location updates, no ETA, no
approach polyline, and no arrival/start/complete events.** The passenger UI has no state for this.

## 1.5 The lifecycle is gated on driver GPS — the central technical problem

| Transition | Gate | Behaviour with no driver GPS |
|---|---|---|
| `ride:arrived` (`:1392`) | within 150 m of pickup (`PICKUP_ARRIVAL_RADIUS_METERS`) | no fix → allowed but **flagged** |
| `ride:start` (`:1477`) | same 150 m gate | no fix → allowed but **flagged** |
| `ride:complete` (`:1553`) | `evaluateCompletion` — destination within 300 m, movement ≥ 100 m, duration ≥ 60 s, GPS freshness | `no_driver_location_at_completion` and `no_meaningful_movement` are **hard** reasons → `paymentHeld = true` |

So if a park-assigned, no-smartphone ride were pushed through the existing handlers, **every single one
would complete held-for-review**, and none of the events could be raised at all (they are driver-socket
handlers keyed on `driverId`). Park Dispatch needs its own, equally strict evidence path. It must not
be built by loosening these gates — they are the anti-fraud spine of the platform.

## 1.6 Admin system

`apps/keke_admin` is a static three-file app (`index.html`, `app.js`, `live_requests.js`) talking to
`/api/v1/admin` with an `X-Admin-Key` header.

`middleware/admin_permissions.ts` maps up to four **environment-variable API keys** to roles
(`superadmin`, `operations`, `support`, `readonly`) with permissions `monitor:read`,
`monitor:reveal_contact`, `metrics:read`, `admin:write`. There is **no admin user table**, no
per-person login, no password, no session; `AuditLog.adminId` stores a role label, not a person.
Notably `requirePermission` and `attachAdminIdentity` both **default to `superadmin`** when no identity
resolves.

Existing capability: overview, driver approve/reject/suspend/activate, document review, active rides,
ride history, held-for-review rides with release/void, finance summary, debt leaderboard, payouts, SOS,
audit log, settings, Live Riders and Live Ride Requests with per-ride dispatch timelines.

**This authentication model cannot be extended to park dispatchers.** A shared environment key is
exactly the anonymous shared credential the brief says to design against.

## 1.7 Location and mapping

Driver positions live only in the Redis GEO set; `GEORADIUS ... WITHDIST/WITHCOORD` drives both
dispatch and the passenger's anonymised nearby-Keke feed (`nearby_keke_feed_service.ts`,
`nearby_marker_service.ts`). Distances are straight-line haversine (`ride_integrity_service.ts:41`);
road routing happens client-side via Google APIs. Coordinates are validated to a Nigeria bounding box
(lat 4–14, lng 2–15) in `socket_handler.ts:75`.

There is no polygon/geofence store, no zone model, and no persistent location for anything that is not
a live driver — a park has nowhere to exist today.

## 1.8 Pre-existing issues Park Dispatch must not inherit or amplify

1. **Passenger phone is sent to every rung driver before assignment.** `buildOfferPayload`
   (`socket_handler.ts:1912`) puts `passengerPhone` in the offer that goes to *all* reserved candidates.
   A park offer must carry **no** passenger contact data until a driver is actually assigned.
2. **Client-generated `rideId`.** Accepted as-is today; park claims must key off it defensively.
3. **`DEBT_HARD_BLOCK` unenforced** — worth fixing while the wallet work is open.
4. **Single-process in-memory dispatch state** (§1.1.1a).
5. **Admin identity is a shared key** (§1.6).

# PART 2 — PRODUCT RECOMMENDATION

## 2.1 Verdict

**Build it — with one substantial correction to the initial concept.**

The operational problem is real and the concept is sound: parks are where supply physically is, and a
trained dispatcher with a working device is a far cheaper fix than pushing smartphones and data onto
every driver. Park Dispatch is genuinely complementary to direct dispatch and can reuse most of the
existing spine (one ride record, atomic assignment, wallet, evidence trail).

**The correction:** step 8 of the initial concept ends at "the ride becomes assigned to that specific
driver" and steps 9–12 implicitly leave the dispatcher driving the lifecycle. That is the single
riskiest idea in the brief. A dispatcher who can mark *arrived*, *started* and *completed* for a driver
who emits no telemetry can manufacture revenue-free trips, inflate fares and collude with drivers — and
nothing in the current integrity model would catch it, because the current model is built entirely on
driver GPS.

**The corrected model:**

> A dispatcher may **claim** a request and **assign** a driver. A dispatcher may **never** advance the
> ride's lifecycle. Post-assignment, either the **driver's app** owns the lifecycle (smartphone driver,
> unchanged from today), or the **passenger's app** does (no-smartphone driver). There is no third path.

This is what makes the feature safe, and it costs nothing operationally — the passenger is present for
every transition by definition.

## 2.2 What this changes for each actor

| Actor | Gains | Explicitly cannot |
|---|---|---|
| Dispatcher | claim, assign, report incident, request cancellation, log attendance | mark arrived/started/completed, edit wallets, see passenger contact before assignment |
| No-smartphone driver | real account, badge, wallet, ledger, ride history, ratings | nothing in-app (they have no app) |
| Smartphone driver | an extra source of work | nothing changes after they confirm — normal flow resumes |
| Passenger | supply where there was none | — |

# PART 3 — RECOMMENDED DISPATCH STRATEGY

**Recommendation: Strategy A — direct drivers first, park fallback.** This matches the stated preference
and is the only option that cannot degrade the working system, because it runs strictly *after* direct
dispatch has already concluded.

## 3.1 The phase sequence

```
ride:request
   │
   ├─ PHASE 1  DIRECT DISPATCH   (unchanged; ≤2 rounds, ≤110 s lifetime)
   │     accepted ──────────────────────────────────► status = accepted   [DONE]
   │     not accepted
   │        │
   │        ├─ no eligible park ─────────────────────► status = failed     [today's behaviour]
   │        │
   │        └─ eligible park exists
   │              │
   │              ▼
   ├─ PHASE 2  PARK OFFER        (ride status stays `searching`)
   │     offer to ONE park; park_decision_window (default 45 s)
   │     no claim / declined ──► next park in priority order, else failed
   │     claimed
   │        │
   │        ▼
   ├─ PHASE 3  DRIVER ASSIGNMENT (ride status still `searching`)
   │     dispatcher must assign within park_assignment_window (default 120 s)
   │     timeout ──► release claim, try next park, else failed
   │     assigned
   │        │
   │        ▼
   └─ PHASE 4  ASSIGNED  →  status = accepted   [one ride, one driver]
```

**Critical implementation point:** Phase 2–3 must live **outside** `DispatchRun`. The orchestrator's
110 s `maxSearchLifetimeMs` and 2-round ceiling are product guarantees for *direct* dispatch and must
not be stretched. The hand-off point is `finalizeUnsuccessfulDispatch` (`socket_handler.ts:1978`):
instead of unconditionally writing `status = 'failed'`, it consults a new `ParkDispatchService`, and
only fails the ride when no park path is available or the park path is exhausted.

## 3.2 Why the invariants survive

| Invariant | How it is preserved |
|---|---|
| One ride ID | Park phases never create a ride row; they create a `ParkRideClaim` referencing the existing `rideId` |
| Passenger active-ride guard | Untouched — status stays `searching` throughout Phases 2–3 |
| Atomic ownership | Park assignment uses the **identical** conditional UPDATE (`WHERE rideId = ? AND status = 'searching'`) as `ride:accept`. Whoever gets there first wins, by construction; there is no new race |
| No duplicate offers | Only one park may hold a claim: Redis `SET park_claim:<rideId> <parkId> NX EX <window>` |
| No duplicate assignment | The DB UPDATE is the sole arbiter, exactly as today |
| No double commission | Settlement is still driven only by `settleAndComplete` → `postRideFinancials`, called once |
| Evidence | New `DispatchEventType` members, projected through the existing pipeline |

**`RideStatus` gains no new values.** Every existing conditional UPDATE, sweeper query and eligibility
filter keeps working unmodified. This is the highest-leverage safety decision in the whole design.

## 3.3 Deliberately deferred

Parallel park+direct offering (Strategy B) and park-first zones (Strategy C) are attractive for
dense-park geographies but multiply the ownership races. Ship A, measure `time_to_park_acceptance` and
`park_assignment_success_rate` at the pilot, and only then consider C behind an ops-configurable
per-park flag (Strategy D).

# PART 4 — PARK ENTITY DESIGN

**A Park is a first-class database entity that also acts as a geo supply node. It is never a driver
account and never merely a coordinate.**

Three facets, one entity:

1. **Operational entity** (Postgres) — identity, roster, dispatchers, devices, hours, config, audit.
2. **Supply node** (Redis) — a member of a `parks:locations` GEO set so `GEORADIUS` can find candidate
   parks for a pickup with the same primitive dispatch already uses.
3. **Geo-zone** (config, not geometry) — `serviceRadiusKm` for launch. **No polygons in v1**: PostGIS is
   not installed, and a radius is sufficient for a pilot. Revisit only if pilot data shows radius
   overlap causing bad park selection.

Two radii, distinct meanings:
- `operatingRadiusM` (~200 m) — how far from the park pin a dispatcher device may be and still be
  considered on-site. Used for shift-start location attestation.
- `serviceRadiusKm` (~4 km) — how far from the park a pickup may be for the park to be offered the ride.

# PART 5 — PARK DISPATCHER DESIGN

**Recommendation: a dispatcher is a person with their own credentials, modelled as a new `User.role`
(`park_dispatcher`) plus a `ParkDispatcher` profile row.**

Why reuse `User`: it gives email+password, bcrypt hashing, email-OTP verification, JWT issuance and
`authMiddleware` for free, with zero new auth code — the same pattern `DriverProfile` already follows.
Why a separate profile row: dispatcher-specific state (assigned parks, employment status, shift
history) must not pollute `DriverProfile`, and **a dispatcher must never be a driver account**.

**A dispatcher is not an admin.** They must not receive an `ADMIN_API_KEY`; the shared-key model has no
personal identity and cannot satisfy the audit requirement.

## 5.1 Non-negotiable controls

| Requirement | Mechanism |
|---|---|
| No shared passwords | One `User` per human; concurrent-session limit of 1 per dispatcher; a second login terminates the first and is logged |
| No anonymous device use | Every dispatcher action carries a `deviceId` from a server-issued, server-bound device credential; unbound device ⇒ 403 |
| Shift-bound authority | Actions are rejected outside an open `DispatcherShift`; opening a shift requires being within `operatingRadiusM` of the park pin |
| Shift handover | Explicit close (with an outstanding-claims summary) before the next shift opens. An unclosed shift auto-closes at `park.closesAt + grace` and is flagged |
| Full attribution | Every action writes `{dispatcherId, parkId, deviceId, driverId?, rideId?, action, reason?, lat, lng, occurredAt}` |

## 5.2 Permission set (dispatcher scope only)

`park:claim_ride` · `park:assign_driver` · `park:lookup_driver` · `park:checkin_driver` ·
`park:report_incident` · `park:request_cancellation` · `park:view_roster`

Explicitly **absent**: any wallet mutation, any ride lifecycle transition, any access to a passenger's
contact details before assignment, any driver approval/suspension, any access to another park.

# PART 6 — DRIVER IDENTIFICATION: QR vs SIX-DIGIT CODE

## 6.1 Decision

**Both, with different jobs. QR is primary; the six-digit code is a typed fallback. Neither is a
credential.**

| | QR badge | Six-digit code |
|---|---|---|
| Role | primary, ~1 s scan | fallback: damaged/lost badge, camera failure, poor light |
| Content | signed opaque token | a lookup key, not a secret |
| Offline verifiable | **yes** (HMAC checks locally) | no |
| Forgeable by hand | no | yes — hence rate limits |
| Server call required to assign | **yes, always** | **yes, always** |

Rationale: a Keke park at 6 a.m. in the rain is a hostile environment for typing. QR handles the 95 %
case in a second and is cryptographically tamper-evident. But badges get lost, wet and sat on, so a
fallback is mandatory — and because a 6-digit space is trivially brute-forced, that fallback must be
rate-limited and can never be the thing that authorises anything.

## 6.2 QR payload

```
KR1|<badgeSerial>|<driverPublicId>|<issuedAtEpochDays>|<sig>

sig = base32( HMAC_SHA256(BADGE_SIGNING_KEY, "KR1|serial|driverPublicId|issuedAtEpochDays")[0..9] )
```

- **`driverPublicId` is a new opaque per-driver identifier, not `User.id`** — the internal uuid should
  not be printed on thousands of paper badges.
- **No PII in the payload.** A photographed QR reveals nothing about the human.
- **Static, not rotating.** Paper cannot rotate. Revocation is by `badgeSerial` status, checked
  server-side on every assignment — which is why the QR does not need to be a secret.
- **80-bit truncated signature** — enough that a forged badge cannot be constructed, small enough for a
  reliable low-density QR that scans off a scuffed laminate.
- Signing key lives in `BADGE_SIGNING_KEY` (env), with a `keyVersion` byte reserved for rotation.

## 6.3 Why the badge cannot authenticate anything

A QR can be photographed from two metres away. Therefore the badge is treated as **an identity claim,
never a credential**. It authorises exactly one thing — "assign *this* ride to *this* driver, right
now, at *this* park, by *this* dispatcher, during *this* shift" — and every one of those qualifiers is
verified server-side.

Hard rule: badge identity must **never** unlock wallet withdrawal, profile modification, account
access, payment reversal or any administrative action.

## 6.4 Post-scan confirmation (mandatory)

After a successful scan or code entry, the dispatcher device shows **driver photo (large), name, unit
number, vehicle plate**, and the dispatcher must tap **"This is the person in front of me"** before the
assignment call is made. This is the control that defeats badge sharing, and it costs one second.

## 6.5 Lifecycle and abuse controls

- **Issue:** `DriverBadge` row per physical badge; only one `active` badge per driver.
- **Revoke:** any status other than `active` → assignment refused, with the reason surfaced on the
  dispatcher device.
- **Replace:** issuing a new badge auto-revokes the previous one; the reason is recorded (`lost`,
  `damaged`, `stolen`, `reissue`).
- **Short-code uniqueness:** 6 digits over a small driver population is fine, but codes must be unique
  across *active* badges and never reused after revocation.
- **Brute force:** per-device rate limit (5 failed lookups / 10 min → 15 min lockout), per-park limit,
  and an alert to admin. Failed lookups are audit events, not silent 404s.
- **Offline:** signature verifies offline so the dispatcher gets instant "valid badge" feedback, but the
  UI must say *"Checking…"* and never *"Assigned"* until the server confirms. See Part 12.

## 6.6 Badge specification (physical)

PVC card, CR80 (85.6 × 54 mm), landscape, laminated, single-sided print.

| Element | Detail |
|---|---|
| Photo | 25 × 32 mm, same image as `DriverProfile.photoUrl` (already KYC-verified) |
| Name | Full name, 14 pt bold |
| Unit number | **Largest element on the card** — this is what a dispatcher reads across a park |
| Vehicle plate | 12 pt, under the unit number |
| QR | 22 × 22 mm, error-correction level **Q** (25 %) — survives scuffing |
| Six-digit code | Printed under the QR, 16 pt, mono, spaced `123 456` |
| Support line | Printed on every badge |
| Serial | Small, bottom edge — matches `DriverBadge.badgeSerial` |
| Not printed | Phone number, address, NIN, email, internal uuid |

# PART 7 — NO-SMARTPHONE DRIVER WORKFLOW

## 7.1 Who does what

| Ride action | Actor | Enforcement |
|---|---|---|
| Accept assignment | **Dispatcher**, on the driver's behalf, after badge scan + photo confirm | server-verified badge, shift, device, park |
| Depart park | Dispatcher taps *"Driver has left the park"* | timestamp only; grants no money and no state change |
| Arrived at pickup | **Passenger** taps *"My Keke is here"* | passenger GPS captured |
| Trip started | **Passenger** taps *"We've started"* — driver reads the 4-char `pickupCode` aloud, passenger confirms it matches | reuses the existing `pickupCode`; proves the right vehicle |
| Trip completed | **Passenger** taps *"Trip finished — I paid ₦X"* | passenger GPS + destination proximity |
| Cash collected | Recorded by the passenger's completion confirmation | never by the dispatcher |
| Cancellation | Either party requests; the existing two-sided flow applies. Dispatcher may *request*, never execute | reuses `ride:cancel_request` semantics |
| Incident | Dispatcher, with a reason | audit event, notifies support |

**The dispatcher never advances the lifecycle.** This is the whole safety model.

## 7.2 Passenger-assisted verification — which mechanism

Evaluated against Nigerian park conditions:

| Option | Verdict |
|---|---|
| Passenger app confirmation + passenger GPS | ✅ **Recommended.** Zero extra artefacts, passenger already has the app and is present |
| Trip-start PIN read aloud (the existing `pickupCode`) | ✅ **Recommended as a companion** — already built, already printed in the UI, proves vehicle identity at boarding |
| Passenger scans the driver's badge QR | ⚠️ Nice-to-have. Strongest boarding proof, but adds a camera step in traffic. Optional, not required |
| One-time SMS code | ❌ Cost, latency and delivery reliability in NG |
| Server-side proximity from the driver | ❌ Impossible — no device |

**So: `pickupCode` for boarding, passenger app taps + passenger GPS for arrival / start / completion.**
This needs no new hardware, no SMS spend, and reuses two mechanisms that already exist and work.

## 7.3 Completion evidence, restated as strictly as the driver-GPS path

Direct rides validate against the *driver's* GPS. Park no-smartphone rides validate against the
*passenger's* — same rules, same thresholds, different source:

| Reason code | Condition | Effect |
|---|---|---|
| `no_meaningful_movement` | passenger start→end < `MIN_TRIP_MOVEMENT_METERS` | **hold** |
| `trip_too_short` | duration < `MIN_TRIP_DURATION_SECONDS` | **hold** |
| `ended_far_from_destination` | > `DESTINATION_COMPLETION_RADIUS_METERS` | hold unless passenger consents (existing early-end flow) |
| `no_passenger_location_at_completion` | no fix | **hold** |
| `passenger_never_confirmed` | window elapsed with no response | complete, **hold**, notify support |

The existing `paymentHeld` / `reviewReason` / admin release-or-void machinery
(`admin_routes.ts:686,719`) handles all of these unchanged.

## 7.4 Passenger location honesty

**Do not show fake live driver movement.** No telemetry exists; drawing a moving marker would be a
fabrication and would destroy trust the first time a Keke arrived from the wrong direction.

Show instead:
- The **park pin** as the trip origin ("Your Keke is coming from Awka Main Park").
- A **one-shot road-distance ETA** computed at assignment (park → pickup), presented as an estimate.
- A **prominent call button** — this is the real tracking mechanism, and it works.
- Driver photo, name, unit number, plate — same card as a direct ride.
- A "Driver hasn't arrived" report action.

## 7.5 A no-smartphone driver still has everything else

Real `User` + `DriverProfile`, KYC documents and selfie, approval status, registered vehicle, physical
badge, wallet, commission ledger, earnings, ride history, suspension state and ratings. They differ
from a smartphone driver in exactly one respect: **`driverDeviceMode = 'park_managed'`**, meaning they
are ineligible for direct dispatch (no heartbeat, so `GEORADIUS` never returns them anyway) and their
rides are lifecycle-driven by the passenger.

# PART 8 — SMARTPHONE-DRIVER HANDOFF WORKFLOW

```
Dispatcher scans badge
        │
        ▼
Server sees driverDeviceMode = 'app'
        │
        ├─► emits ride:park_assignment to driver:<id> + FCM push
        │   Ride stays `searching`. NOTHING is assigned yet.
        │
        ├─ driver confirms in-app (≤ park_driver_confirm_window, default 60 s)
        │        │
        │        ▼
        │   the SAME conditional UPDATE searching→accepted
        │   → normal ride, normal gates, normal telemetry
        │   → dispatcher device shows "Confirmed — driver has the ride"
        │   → dispatcher loses ALL further control of this ride
        │
        └─ no confirmation within the window
                 │
                 ▼
             assignment lapses; dispatcher device shows
             "Driver did not confirm — assign someone else"
             Park claim survives if the assignment window still has time.
```

**Conflicting-transition prevention is structural, not defensive:** post-assignment, dispatcher
lifecycle endpoints return `409 PARK_ASSIGNMENT_HANDED_OFF` for any ride whose
`driverDeviceMode = 'app'`. There is no code path in which both a dispatcher and a driver app can
advance the same ride, because dispatchers have no lifecycle endpoints at all (Part 7.1).

**Why require explicit confirmation?** It proves possession of the phone and consent to the trip. A
silent push-assignment would let a dispatcher dump rides on a driver who is asleep, and the ride would
then die in the stale-recovery flow with the passenger waiting.

# PART 9 — WALLET AND COMMISSION RECOMMENDATION

**Recommendation: Model C (Hybrid), as preferred — and it is very nearly what the code already does.**

`_postCashRideFinancials` already deducts commission from `driverAvailableBalance` and pushes the
shortfall into `driverCommissionDebt`; `filterCashEligibleDrivers` already blocks at ₦2,000. Hybrid is
the existing model. Park Dispatch needs three additions, not a rewrite.

### Addition 1 — Enforce the credit limit on the park path

Park assignment must apply the same eligibility filter as direct dispatch. `DriverEligibilityService`
should be reused verbatim (it is already the single definition of eligibility, deliberately shared
between dispatch and the map feed). A debt-blocked driver must be **visibly** refused on the dispatcher
device with the amount owed, so the dispatcher can send them to the cashier instead of guessing.

Also: **enforce or delete `DEBT_HARD_BLOCK`.** Dead thresholds are worse than none.

### Addition 2 — A real cash-in path (the biggest gap)

Today the only way debt reduces is a Paystack top-up or wallet earnings. A no-smartphone driver has
neither. Without a cash-in path, every park driver hits the ₦2,000 block within a handful of trips and
the pilot dies on day two.

Proposal — **an authorised cashier role**, not the dispatcher:

- New `User.role = 'park_cashier'` (may be the same human as a dispatcher **only** where the pilot's
  size makes separation impossible — and then it must be flagged as a known control weakness in the
  pilot risk register, with 100 % of those transactions reconciled daily).
- `CashCollection` record: `{driverId, parkId, cashierId, deviceId, amount, method, referenceOrProof,
  collectedAt, reconciledAt, reconciledBy, status}`.
- Effect on the wallet: a `DEBT_RECOVERY` / `TOPUP` `LedgerEntry` pair through
  `WalletService.mutateBalance` — **the existing ledger API, never a direct balance write**.
- Two-stage: `pending_reconciliation` → `reconciled`. Debt relief is granted immediately (the driver
  must get back on the road) but the collection stays open until finance matches it against a bank
  deposit. Unreconciled float per cashier is capped and monitored.
- Receipt: printed/shown reference plus an SMS to the driver's phone. Nigerian drivers will not accept
  a cash handover with no receipt, and they are right not to.

### Addition 3 — Park-level settlement configuration

`Park.commissionConfig` reserved for a future park-share model. **Not used in v1** — flat platform
commission only. Introducing a revenue share before the unit economics are measured would be premature.

### Hard rule

> A dispatcher (or cashier) may **never** edit a wallet balance. Every monetary movement goes through
> `WalletService`, produces `LedgerEntry` rows with `balanceBefore`/`balanceAfter`, and is attributable
> to a named human, a device and a shift.

# PART 10 — CASH SETTLEMENT ARCHITECTURE

```
Passenger pays driver cash
        │
        ▼
Passenger confirms completion in-app ("Trip finished — I paid ₦1,500")
        │
        ▼
Integrity evaluation on PASSENGER GPS  ──── fails ───► paymentHeld = true
        │ passes                                        (admin release/void)
        ▼
WalletService.postRideFinancials(isCash: true)   [existing code, unchanged]
        │
        ├─ CASH_RECEIVED        (audit row; balance unchanged)
        ├─ COMMISSION_CHARGE    (from driverAvailableBalance)
        ├─ shortfall            → driverCommissionDebt
        └─ PLATFORM_REVENUE     (entry-only)
        │
        ▼
Debt ≥ ₦2,000  ──► driver blocked from further cash rides (direct AND park)
        │
        ▼
Driver pays cash to the park CASHIER
        │
        ├─ CashCollection (pending_reconciliation) → debt relief posted immediately
        ├─ SMS receipt to driver
        └─ Daily reconciliation against bank deposit → status = reconciled
```

**Disputes.** A passenger who denies a trip, or a driver who denies collecting the fare, opens a
`RideDispute` (ride, party, claim, evidence refs, resolution, resolver, timestamps). While open, the
ride's money is held using the existing `paymentHeld` mechanism. Resolution is admin-only, audited, and
reverses through `LedgerEntry` — never by editing a balance.

# PART 11 — FRAUD AND RISK ANALYSIS

| # | Risk | Technical mitigation | Operational mitigation |
|---|---|---|---|
| 1 | Dispatcher assigns a "ghost" driver | Assignment requires an `active` badge on an `approved` driver checked into the park within the last N hours | Roster audit; unit-number spot checks |
| 2 | Badge shared between drivers | Mandatory photo-confirm screen before assignment | Random park inspections; badge confiscation policy |
| 3 | Dispatcher completes a fake trip | **Structurally impossible** — dispatchers have no completion endpoint | — |
| 4 | Passenger + driver collude to hide a cash fare | Requires the passenger to never book — out of scope | Passenger incentives (points/receipts) |
| 5 | Dispatcher-driver collusion (assignment bias) | Per-dispatcher/per-driver assignment concentration metric; override reason required and logged | Rotate dispatchers between parks |
| 6 | Cashier collects and does not remit | Two-stage `CashCollection`, per-cashier float cap, daily reconciliation, alert on ageing float | Separation of duties; surprise cash counts |
| 7 | Driver uses a different vehicle | Plate + unit shown on the photo-confirm screen; passenger sees the plate and can report a mismatch | Incident workflow |
| 8 | Overlapping trips for one driver | `DriverEligibilityService` "already on active ride" applies identically on the park path | — |
| 9 | QR photographed and reused | Badge is not a credential; assignment additionally requires shift + device + park + photo-confirm | — |
| 10 | Six-digit code guessed | Per-device and per-park rate limits, lockout, alert; codes unique across active badges | — |
| 11 | Park device stolen | Remote revoke of the device credential; shift auto-close; kiosk lock; PIN on wake | Report-and-revoke SOP |
| 12 | Dispatcher account shared | One session per dispatcher; second login kills the first and is logged; shift start needs on-site GPS | Employment policy |
| 13 | Offline actions replayed | Every assignment carries a client-generated idempotency key; server dedupes | — |
| 14 | Driver swapped after assignment | Reassignment is a distinct, reason-required, audited action visible to the passenger | — |
| 15 | Passenger contact exposed unnecessarily | Park offers carry **no** passenger contact; phone is released only on assignment, to the assigned driver (and to the dispatcher only if `park:reveal_contact` is granted for a live incident) | Contact-reveal audit |
| 16 | Inflated fares | Fare is already server-authoritative (`finalFare`); the client value is audit-only | — |

# PART 12 — OFFLINE AND POOR CONNECTIVITY

**Principle: fail-safe. Nothing that assigns work or moves money may complete offline.**

| Action | Offline? | Rationale |
|---|---|---|
| Viewing the roster / queue | ✅ cached, with a visible "last updated" age | Read-only |
| Decoding + signature-verifying a QR | ✅ | HMAC verifies locally; instant "valid badge" feedback |
| Checking a driver into the park | ⚠️ queued, clearly marked *Pending* | Attendance, not assignment |
| **Claiming a ride** | ❌ | Two parks could both claim |
| **Assigning a driver** | ❌ | Two drivers for one passenger — the exact outcome the brief forbids |
| **Anything monetary** | ❌ | — |

UI contract: while offline, the assign button reads **"Waiting for network…"** and is disabled. A queued
action never renders as success. Every online assignment carries an idempotency key so a retry after a
flaky response cannot double-assign.

Duplicate prevention rests on the same two locks as everything else: Redis `NX` on the park claim, and
the conditional `searching → accepted` UPDATE. Neither can be satisfied twice.

# PART 18 — PARK ROSTER AND QUEUE FAIRNESS

**Recommendation for launch: FIFO by check-in, with audited skips and a bias report.**

FIFO is the model parks already use informally, so it needs no explanation to drivers and it is the
only model whose violations are self-evident to everyone standing in the queue. Anything cleverer
(destination rotation, distance-suitability scoring) is unverifiable by the people it affects, which is
precisely what breeds the "the dispatcher favours his friends" complaint.

Mechanics:
- Driver checks in (badge scan) → gets a queue position.
- Assignment defaults to the next `available` driver; the device shows who that is.
- Any other choice is an **override** requiring a reason from a fixed list: `driver_declined`,
  `vehicle_unsuitable`, `wallet_blocked`, `driver_absent`, `already_assigned`, `suspended`,
  `passenger_request`, `other (free text)`.
- Skipped drivers keep their position (they are not punished for a system-side reason).
- Assigned drivers go to the back on completion.
- Admin sees a per-dispatcher concentration metric and an override-rate report.

Not for v1: destination rotation, driver-choice bidding, distance-based scoring. Revisit with pilot data.

# PART 19 — PARK DEVICE

**Recommendation: a dedicated, KekeRide-owned Android device per park, in kiosk mode.** A dispatcher's
personal phone cannot be locked down, wiped or reliably attested, and a lost personal phone is a lost
dispatch point.

| Concern | Approach |
|---|---|
| Binding | One-time admin-generated enrolment code → device credential stored in `flutter_secure_storage` (already used in both apps) |
| Kiosk | Android screen pinning / lock-task mode; PIN on wake |
| Shift login | Dispatcher credentials on top of the device credential — **both** are required |
| Remote logout | Admin revokes the device credential; next request → 401 → forced logout |
| Location check | Verified once at shift start against `operatingRadiusM`; recorded on sensitive actions |
| Tamper | Device credential + app-signature check; failed attestation blocks sensitive actions and alerts admin |
| Updates | Minimum-version gate on the API; below it the app blocks with an update prompt |
| Connectivity | KekeRide-sponsored data SIM; connectivity monitored as a device-health metric |
| Power | Mains + power bank; battery reported in health telemetry with a low-battery alert |
| Theft | Report → immediate revoke; open shift auto-closed; claims released |
| Multiple dispatchers | Several dispatchers may use one device sequentially via shift login. Concurrent shifts on one device are refused |
| Health monitoring | Heartbeat every 60 s → admin device-health view (last seen, version, battery, connectivity) |

> **A park is never represented by one permanently shared personal account.** Device identity and human
> identity are separate credentials, and both are always required.

# PART 22 — DECISIONS, FILES, AND RISKS

## 22.1 What can be built immediately (no policy approval)

- Phase 1 data model and migrations (additive, nullable, no behaviour change).
- `Park` entity, `parks:locations` Redis GEO node and the park-selection query.
- `DriverBadge` model, QR payload signing/verification, badge PDF generation.
- Dispatcher app skeleton, shift model, device binding.
- Extending `DispatchEventType` and the admin ride timeline.
- Passenger copy and UI states for "checking a nearby Keke park".

## 22.2 What needs policy approval before building

1. **Dispatcher employment model** — employees, contractors or commissioned agents? Determines
   liability, whether they can also be cashiers, and the disciplinary process behind an audit finding.
2. **Cashier separation of duties** — can one human be both dispatcher and cashier at a pilot park?
   (If yes, it is a documented, monitored control weakness.)
3. **Passenger data policy** — may a dispatcher ever see a passenger phone number, and under what
   incident conditions?
4. **Badge issuance** — who is authorised to issue and revoke, what is the replacement fee, what is the
   lost-badge SOP?
5. **Park commercial terms** — flat platform commission in v1, or a park revenue share? (Recommendation:
   flat, revisit post-pilot.)
6. **Device ownership and loss liability.**

## 22.3 What requires financial controls sign-off

Phase 7 in full: the cashier role, `CashCollection`, float limits, reconciliation, receipts, dispute
resolution and reversal authority. **No cash-handling code should be written before these controls are
agreed in writing**, because the control design determines the data model, not the reverse.

## 22.4 What should be postponed

Park revenue sharing · polygon geofences / PostGIS · GPS trackers on Kekes · USSD/IVR driver channel ·
parallel park+direct dispatch (Strategy B) · park-first zones (Strategy C) · destination-rotation
fairness · multi-park sequential fallback beyond two parks · dispatcher performance-based pay.

## 22.5 What should never be implemented

1. **A dispatcher completing a ride** — the fraud vector with no technical defence.
2. **A dispatcher (or anyone) editing a wallet balance directly.** All money moves through
   `WalletService` and leaves `LedgerEntry` rows.
3. **Fake live driver movement** for a driver with no telemetry.
4. **One shared park login** used by whoever is on duty.
5. **The QR or six-digit code as an authentication credential** for wallet, profile or account access.
6. **Offline assignment or offline monetary actions.**
7. **A dispatcher account that is also a driver account.**
8. **Weakening the existing GPS gates** (`evaluateProximityGate`, `evaluateCompletion`) to accommodate
   park rides. Park rides get their own equally strict evidence path.
9. **Storing badge signing material on the dispatcher device.** Verification only; signing is server-side.
10. **Auto-approving a park ride's payment when the passenger never confirms.** It completes *held*.

## 22.7 Risks to the currently working dispatch system

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | The `finalizeUnsuccessfulDispatch` edit changes direct-dispatch failure behaviour | medium | **high** | Feature flag; early return to the exact existing path when no park is eligible; regression tests over the existing dispatch suite before and after |
| 2 | A ride sits in `searching` far longer than today (park windows extend beyond 110 s) — the stale sweeper and the passenger's UI both have opinions about a long search | **high** | **high** | Explicitly extend/park-aware the sweeper's `searching` handling and the passenger's searching timeout **in the same change**. This is the most under-appreciated risk in the whole design |
| 3 | Passenger active-ride slot (3 h TTL) held longer, delaying rebooking after a failed park path | medium | medium | Release the slot on park exhaustion exactly as `finalizeUnsuccessfulDispatch` does today |
| 4 | New `RideStatus` values would break every conditional UPDATE and sweeper query | low (by design) | critical | **Design rule: no new `RideStatus` values.** Enforce in review |
| 5 | Redis key-space growth / new lock families interacting with driver reservations | low | medium | Namespace park keys (`park:*`); never reuse `driver:reserved:*` semantics |
| 6 | In-memory dispatch state invisible to HTTP dispatcher calls (§1.1.1a) | **certain** if scaled | high | Park state in Redis+Postgres only; a Redis pub/sub channel to signal the socket process; document the single-process assumption |
| 7 | Enum migrations on a live Postgres (`ALTER TYPE ... ADD VALUE`) | medium | medium | Follow the existing pattern in `1746600000000` / `1756600000000`; separate transaction |
| 8 | Older passenger/driver APKs receiving unknown events | **high** | low | Additive events only; old builds ignore unknown socket events, as with the coordination rollout |
| 9 | Dispatcher app load on the backend (polling/sockets) | low | low | Socket rooms per park; no polling |
| 10 | Ops complexity: a second human class to train, monitor and pay | **high** | medium | Contained pilot; explicit dispatcher SOP; abort triggers |

## 22.8 Open product decisions requiring approval

| # | Decision | Recommendation |
|---|---|---|
| 1 | Park fallback trigger — always after direct exhaustion, or only when direct found zero candidates? | **Always after exhaustion.** Simpler, and rejection is as much a supply failure as absence |
| 2 | Sequential park fallback depth | **Two parks maximum**, then fail. Beyond that the passenger has waited too long |
| 3 | Park decision window | **45 s** offer, **120 s** to assign |
| 4 | Total worst-case passenger wait | 110 s direct + 165 s park ≈ **4.5 minutes**. Acceptable? This needs an explicit product answer — it is nearly 2.5× today's ceiling |
| 5 | May a park claim a ride during round 2 rather than after it? | **No in v1** (Strategy A). Revisit with data |
| 6 | Can a `park_managed` driver ever take a wallet-paid ride? | **Yes** — payment mode is independent of device mode; passenger pays from wallet, driver is credited net |
| 7 | Passenger completion window before auto-complete-and-hold | **30 minutes**, then complete with `paymentHeld` |
| 8 | Does the passenger see that the ride came from a park? | **No.** The driver card is identical |
| 9 | Dispatcher access to passenger phone | **Never before assignment.** After assignment, only under an incident, gated and audited |
| 10 | Can one human be both dispatcher and cashier at the pilot park? | Policy call — see §22.2 |

## Summary

Park Dispatch is worth building and fits the existing architecture cleanly, provided three rules hold:

1. **The dispatcher assigns; they never advance the lifecycle.** Post-assignment the driver app or the
   passenger app owns the ride, and there is no third path.
2. **`RideStatus` gains no new values, and assignment goes through the existing conditional UPDATE.**
   Every current invariant — one ride, atomic ownership, no double commission — then holds for free.
3. **Park rides get their own evidence path, as strict as the driver-GPS one.** Passenger GPS and
   confirmation replace driver GPS; the existing thresholds, `paymentHeld` and the admin
   release/void workflow are reused unchanged.

The two most under-appreciated risks are the **stale-ride sweeper and passenger UI reacting to a
much longer `searching` phase** (§22.7 #2), and the **absence of any cash-in path for a driver who has
no smartphone and no bank app** (§9, Addition 2). Both must be solved in the same phases that create
them, not afterwards.
